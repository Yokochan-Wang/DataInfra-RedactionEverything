# laya 句级"敏感判定"可行性实验方案

> 本文先写门槛，再跑实验——门槛写进文档后不再修改，避免事后挑数字。
> 状态：Stage 0 已完成（结论见第 0 节，**它改变了本实验的目的**）。

---

## 0. Stage 0（已完成）：先量真实负载，判断这个方向值不值得做

原始提案是"用 laya 并行判断 10 句话是否含敏感信息，用作剪枝以提效"。
剪枝能否提效，只取决于一件事：现在有多少文本因为容量上限而"该发没发"，以及有多少 LLM 调用能被省掉。

### 实测数据（本仓库真实数据）

    数据源: backend/data/file_store.sqlite3   file_store 表, 112 份真实文档
    窗口  : backend/uploads/*.txt, 102 份文本单元

    单份文档正文字符数:  min 0 | 中位 830 | p90 3,787 | p99 3,787 | max 169,359

对比当前管线的容量上限（读代码得到）：

    MAX_HAS_TEXT_CHARS = 1,600     每个 chunk 的字符上限
    MAX_HAS_CHUNKS     = 12        每篇文档最多 12 个 chunk
    ⇒ 上限 = 19,200 字符

| 判据 | 实测 | 含义 |
|---|---|---|
| 单份文档正文字符数 | 中位 **830** | ≤1600 ⇒ 本来只要 1 个 chunk（1 次 LLM 调用） |
| 超过 1600 字符（≥2 chunk） | 24 / 112 = **21.4%** | 最多也就 2-3 个 chunk |
| 超过 12-chunk 上限（19,200） | **1 / 112 = 0.9%** | 只有那 1 份 169 KB 文档被截断，覆盖 11% |

### 结论（这就是本实验最大的先验信息）

1. **剪枝提效不成立。** 中位 830 字符的文档本来只需 1 次调用；剪枝无法把调用数降到 1 以下。
   它只能减少发出去的字符数，而一次 830 字符的调用和一次 600 字符的调用，延迟几乎无差别。
2. **排序也无收益。** 12-chunk 上限只被 1/112 的文档触及，"把重要的行排前面"没有可操作空间。
3. **净成本是正的。** laya 每份文档要跑 ~34 行（3467 行 / 102 份），按 ~7 ms/句 ≈ **+240 ms/份**，
   而它省不掉任何一次 LLM 调用 ⇒ **总体更慢**。
4. **唯一有价值的方向是反过来**：那 1 份 169 KB 的文档现在只覆盖 11%，是召回受损场景。
   在那里需要的是"排序 / 扩预算"，**不是剪枝**。

### 因此实验目的必须修正

原命题"剪枝提效"**已被数据否决**，不必再花时间验证。调整后本实验要回答的是：

> **laya 的句级敏感判定准不准、稳不稳、够不够快？**
> —— 决定它能否用于 (a) 长文档的行排序（召回导向），或 (b) 整篇无敏感内容时的 skip 门。

如果连这个也过不了，那就是彻底不用。

## 1. 实验要验证什么：4 个可独立证伪的假设

把"能不能用"拆成 4 个互相独立的假设。这样失败时可以归因（是模型不行？批处理有 bug？还是收益不够？），
而不是得到一个"不行"的笼统结论。

### H1 判别有效性（必要前提，死了就没后面）
> laya 对单句的"是否含敏感信息"判定，在你自己的中文脱敏域上足够准：
> **identity 类句子的召回 = 100%**（无漏检），且能识别出相当比例的背景句。

- **证伪条件**：identity 句召回 < 100%（只要漏 1 句就否决）
- 为什么这是前提：剪枝/排序都是在做"哪些内容不重要"的判断，判错的方向如果是"把敏感句判成不重要"，代价是数据泄漏。
- 失败后果：整个方案作废，不进入 H2/H3。

### H2 判定自洽性（纯工程正确性，不需要真值）
> 把 N 句话打包进一个 state、一次前向出 K 个答案，与逐句单独跑相比，判定结果不改变；
> 且不会因为 token 预算把句子静默丢掉。

- **证伪条件**：identity 句在 batch=1 与 batch=N 之间出现翻转（>0 次），或存在"送进去的句子数 > 判定出的句子数"。
- 为什么必须单独测：laya 的 state 是双向注意力的，10 句互可见；"并行"本身可能引入错误。
  这跟模型准不准是两件事——模型很准但批处理污染，一样会漏。
- 失败后果：放弃批量，退回逐句（速度优势消失），或改用极小批次。

### H3 收益真实性（决定值不值得接）
> 在长文档（>19,200 字符）上，用 laya 的行打分做排序，端到端召回不降且耗时下降。

- **证伪条件**：召回下降（任何幅度），或耗时下降 < 10%
- 为什么限定长文档：第 0 节已证明短文档没有收益空间。只有长文档（当前 0.9%，但那 169 KB 说明会存在）才有。
- 失败后果：不接入生产，仅在长文档场景保留实验分支。

### H4 升级信号可用性（决定能否做成 cascade 而不是硬门）
> laya 自带 action.act_probability（act / escalate 双类头）能识别"我这次判错了"：对判错样本的 AUC ≥ 0.7。

- **证伪条件**：AUC < 0.7
- 为什么值得测：如果 H1 只能做到 99% 而不是 100%，唯一安全的补救是把不确定的句子交给 LLM 复核。
  那需要"不确定"这个信号是真信号。而 laya 的 confidence 对 noul 恒等于 max(p, 1-p)——
  与概率同源，不含额外信息，不能用来做这件事；只有独立的 act 头还有希望。

## 2. 数据与真值：为什么不需要人工标注就能算召回

### 数据源

`e2e/corpus/{finance,gov,legal,medical}/expected.json` + 同目录 *.txt
真值已经是实体级的，并且已分成两类：

| 类别 | 内容 | 现有门槛 |
|---|---|---|
| identity | 姓名 / 身份证 / 手机 / 银行卡 | **召回 = 100%**（e2e/industry_recall.py: IDENTITY_MIN_RECALL = 1.0） |
| standard | 邮箱 / 地址 / 机构名 | 召回 ≥ 85% |

### 句级标签怎么来（机械推导，不是"推断"）

1. 用与管线完全相同的切句器（hybrid_ner_service._iter_semantic_lines + MAX_HAS_LINE_CHARS=320）切句
2. 对每个句子，检查每条真值实体的 text 是否为该句的子串
3. 标签：含 identity 实体 ⇒ IDENT；只含 standard ⇒ STD；都不含 ⇒ BG

**为什么这是精确的、不是有噪声的推断**：真值 text 是从原文字面复制的，中文没有分词/大小写/空白歧义，
所以"该句是否包含该实体"是确定性的字符串判定，没有标注歧义。

**唯一的边界情况（必须处理并报告）**：切句恰好把实体切成两半 ⇒ 没有任何一句包含完整实体 ⇒ 会被误标成 BG。
处理方式：丢弃这类实体，并报告丢弃数量；丢弃数 > 0 时要人工看一眼切句规则，必要时调整。

### 两类指标的可信度不同（重要）

| 指标 | 是否需要人工核对 | 原因 |
|---|---|---|
| **召回（Recall）** | **不需要** | 真值是"已知敏感"的清单，模型漏了就是漏了，不存在真值本身错的可能 |
| **精确率（Precision）** | **需要** | 语料的真值只覆盖 identity/standard 两类；某句可能含未标注的敏感信息（如未列出的机构名），会被算成误报 |

做法：精确率只需要人工过一遍"被 laya 判为敏感、但真值里没有"的句子清单（量级几十条），标记其中的真误报。
这是本实验唯一的标注成本，且只影响"能剪掉多少"这个收益判断，不影响"会不会漏"这个生死判断。

### 合成增强（为什么必须加）

黄金语料约 20 篇、几百句，其中 identity 句大约 60-120 句。
**在 100 句上做到 100% 召回，只能把真实漏检率的上界压到约 3%**（Wilson 95% 上界）——
即"没发现反例"不等于"证明了 100%"。

更有效率的做法是主动制造反例，而不是扩大真实语料。把真值实体埋进一批模板句，专门覆盖已知的困难形态：

| 干扰形态 | 例子 | 为什么它可能骗过 laya |
|---|---|---|
| 实体嵌在长数字串里 | 账号6217001234509876543 | 边界判定（regex floor 的注释里专门讨论过这个坑） |
| 中英混排 | Name: 张建国 / ID: 310101198803124567 | 编码器是 mmBERT，混排 token 预算紧张 |
| OCR 错字 | 身份证号 1101O1199001011234（字母 O） | 破坏字形，模型可能不再认作证号 |
| 同一句多实体 | 姓名+证号+卡号挤在一句 | 单句可能超 token 预算 |
| 超长句 | >200 字的一段话里埋一个姓名 | 右侧截断风险 |
| 极短句 | 联系人：李四 | 上下文不足 |
| 表格行 | 张三 / 13800138000 / 北京 | 无自然语言结构 |

这一步把 identity 句样本量从 ~100 提到 ~500+，成本几乎为零（本地生成），
并且它测的是"召回"这个生死指标，比扩大真实语料划算得多。

## 3. 实验因子与步骤

### 3.1 因子（都是本地推理，无 API 成本，可以全跑）

| 因子 | 取值 | 想回答的问题 |
|---|---|---|
| A 问题粒度 | A1 粗：该句是否含个人敏感信息？ / A2 细：该句是否含姓名、证号、电话、卡号？ / A3 逐类：姓名、证号、电话、卡号 各一问 | 粗问题可能过度保守（全判敏感→没法用）；细问题可能召回不足 |
| B 批次大小 | 1 / 5 / 10 | 测跨句污染与截断（对照 H2） |
| C 判定阈值 | 扫描 0.5-0.95 | 只有要做硬门时才需要；算 P/R 曲线 |

### 3.2 步骤

**Step 1 极性正负对照（10 分钟，必须先做）**

用 1 句明显含姓名的话 + 1 句明显不含的话，各问一次 noul，确认 noul 在高概率侧对应"成立"、低概率侧对应"不成立"。

为什么必须先做：render_options 对 noul 固定渲染成 [false, true]，返回的 p[1] 是"成立"的概率。
**如果极性搞反，整张记分卡会完全颠倒**，后面所有结论都反了。这一步是防止实验本身出错，不是测模型。

**Step 2 生成句级数据集**

切句 → 贴标签 → 合成增强 → 落盘 sentence_dataset.jsonl
（字段：doc, sent, start, end, label, origin: gold|synthetic, entities）

**Step 3 跑 Stage 1（H1）：逐句判定（batch=1 + A1/A2/A3）**

| 指标 | 门槛 |
|---|---|
| identity 句召回 | **= 100%（0 漏检）** |
| standard 句召回 | ≥ 85%（对齐现有门槛） |
| 背景句正确率 | 报告（决定能剪多少） |
| 背景句的 noul 分离度（AUC） | 报告（决定排序用途是否可行） |

**早退规则：identity 召回 < 100% ⇒ 直接停止，输出否定结论。**

**Step 4 跑 Stage 2（H2）：批次一致性**

同一批句子分别以 batch=1 / 5 / 10 跑，统计：判定翻转率（整体 / 仅 identity 句）、送进去 vs 判出来的句子数（截断检测）。

| 指标 | 门槛 |
|---|---|
| identity 句翻转数 | **= 0** |
| 静默截断 | **= 0** |

**Step 5 跑 Stage 3（H3）：长文档端到端**

在离线重放里模拟 12-chunk 预算：原顺序 vs laya 打分行序，比较黄金实体召回（尤其那份 169 KB 文档）、chunk 数、字符数、模拟耗时。
门槛：召回不降 且 耗时下降 ≥ 10%。

**Step 6 跑 Stage 4（H4）：act_probability 与判错的相关性**

算 AUC。门槛 ≥ 0.7 才值得做 cascade。

**Step 7 出记分卡**

laya_ver/exp/artifacts/report.md：每阶段结论 + 是否过门 + 原始数据。

## 4. 为什么这样设计能达到验证效果（逐条方法论证）

### 4.1 为什么用"离线黄金语料重放"而不是线上 A/B
- 线上试剪枝的风险是**数据泄漏**（漏掉敏感信息），这是不可逆的。离线重放零风险。
- 线上流量无法回答"漏了什么"——没有真值。离线有真值，才能算召回。
- 可重复、可回归：改一行参数就能重跑同一批句子，不会被流量波动干扰。

### 4.2 为什么必须把 H1/H2/H3/H4 分开测
如果只做"端到端跑一遍看结果"，四种失败会混在一起：模型不准 / 批处理污染 / 没有收益空间 / 置信度不可用——
**你无法知道该修哪个**。分开测之后，每一层的失败有明确含义和明确动作（见第 1 节"失败后果"）。

### 4.3 为什么必须用与管线相同的切句器
因为**决策是在切好的行上做的**。用另一套切句规则，测出来的召回无法映射回管线实际会看到的内容；
而且实体的"句子边界"会变，真值贴标就会错位。这是"测得准"的前提。

### 4.4 为什么召回用真值、精确率要人看
召回的反面是"漏"，而真值清单就是"必须不能漏"的集合——模型漏了，责任 100% 在模型，不存在真值噪声。
精确率的反面是"误报"，而"误报"需要知道"这句到底有没有敏感信息"——语料只标注了两类实体，
语料外的敏感内容会被算成误报。所以精确率必须人工核，否则会**低估** laya。

### 4.5 为什么"小样本能否决、不能证明"——以及为什么用合成增强
- 100 句全对，真实的漏检率上界仍有 ~3%。所以通过小样本 = 没找到反例 ≠ 已证明 100%。
- 反过来，在小而干净的语料上漏 1 句，是**强证据**（因为它是精心构造的、容易命中的样本）。
  这就是"能否决不能证明"的统计不对称性。
- 因此把力气花在制造反例（合成增强的 7 类干扰形态）上：同样成本下把样本量提到 5 倍，
  并且样本质量更高（专打已知难点）。
- 报告里必须写明：Stage 1 通过后的**残余风险**（当前语料规模下的漏检率上界），供最终决策参考。

### 4.6 为什么先做极性对照
见 Step 1。这是**实验自身的有效性检验**：如果极性反了，那张"召回 0%"的记分卡并不是模型的结论，
而是脚本的 bug。任何"用概率当证据"的实验，都必须先证明"概率高 = 我以为的那个意思"。

### 4.7 为什么不能拿 laya 自己的 confidence 当第二信号
读代码得到：noul 的 confidence 就是 max(p, 1-p)，**只是概率的另一种写法**。
"低置信就升级"和"用概率阈值"是同一个规则，不会带来任何额外信息。
真正独立的是 action.act_probability（另一个 head），所以 H4 单独测它。

### 4.8 为什么必须 pin 版本（一个已发现的坑）
laya 0.3.4 会把检查点自带的 temperature 直接乘到 logits 上。官方 0.3.5 的注释指出
choice:11+ 桶的拟合值是 **0.1006**，会把 logits 放大约 10 倍：**真实 0.24 的概率被发布成 0.99**。
0.3.5 加了 clamp_temperature（限制到 0.5-5.0）并在越界时告警。

对本项目正在用的检查点，已核对 laya_ver/laya-multilingual/rl_agent_config.json：

    "temperature": [1.0, 1.0, 1.0],
    "temperature_by_options": {}

⇒ 该检查点**不施加任何温度**，noul（k=2）走 temperature[2] = 1.0，**不受这个 bug 影响**。
但仍然必须 pin 具体版本并在报告里记录，否则换版本后数字无法对比。

同时这留下一个重要结论：该检查点的概率是**原始 softmax、未经标定**。
对 2 类问题，这意味着概率容易饱和到接近 0/1，
"0.93 和 0.98 的差别"几乎没有信息量 ⇒ **阈值要扫描，不要凭直觉定 0.9**（这正是因子 C 存在的理由）。
